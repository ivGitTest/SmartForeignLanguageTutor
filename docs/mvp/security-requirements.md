# Требования к безопасности MVP

**Версия:** 0.3 · **Дата:** 13 октября 2026

**Статус:** СОГЛАСОВАНО пользователем без исключений.

**Архитектура:** пользовательский ключ на Android, прямой HTTPS к OpenRouter; своего сервера нет.

**Термины:** [единый словарь](../terminology.md). В MVP нет регистрации, авторизации, паролей, профилей и сессий входа приложения. Защита входа — средствами ОС. Заголовок HTTP `Authorization` для OpenRouter — транспорт пользовательского API-ключа, не система входа приложения.

## 1. Цель и предел защиты

Главная цель — не включить ключи в сборку/Git и не раскрыть сохранённый пользовательский ключ через интерфейс, обычные файлы, логи, резервные копии или посторонние сетевые адреса.

Пользователь вводит свой ключ; приложение должно получить его в памяти для отправки OpenRouter. Поэтому абсолютная защита от владельца рутованного устройства, инструментирования процесса или вредоносной ОС невозможна. SecureStore/Keystore защищает хранение, но не устраняет этот остаточный риск. Обфускация не заменяет защищённое хранилище.

Активы: ключ OpenRouter, аудио, транскрипты и переводы, словарь, прогресс, разрешение микрофона. Основные угрозы: извлечение APK, чтение файлов/backup, утечка через диагностику, подмена адреса, чтение экрана, вредоносный текст и непреднамеренные расходы.

## 2. Хранение и жизненный цикл ключа

| ID | Требование |
|---|---|
| SEC-KEY-01 | Никаких пользовательских или общих ключей в исходниках, APK/AAB, JS bundle, app config, OTA-обновлениях, assets, тестовых fixtures и документации. `EXPO_PUBLIC_*`, `.env` и скрытое поле UI не являются хранилищем runtime-ключа. |
| SEC-KEY-02 | На Android хранить только через `expo-secure-store`, шифрование с использованием Android Keystore. Не SQLite, AsyncStorage, обычный JSON, SharedPreferences без шифрования или публичные каталоги. |
| SEC-KEY-03 | Прочитать ключ только в сетевом адаптере перед запросом; не передавать в глобальное состояние UI, query cache, аналитику или сохранённые снимки операции. После запроса освобождать ссылки; не обещать гарантированное зануление памяти JavaScript. |
| SEC-KEY-04 | Ввод маскирован; после сохранения очистить поле/локальное состояние. Сохранённый ключ не загружать назад в поле. Показывать только «Ключ сохранён» и необязательные последние 4 символа; нет команды скопировать/экспортировать/показать весь сохранённый ключ. |
| SEC-KEY-05 | Пользователь может вставить ключ, но приложение не читает буфер обмена автоматически и не копирует туда ключ. Отключить автозаполнение/предсказание для поля, насколько позволяет ОС; предупредить об остаточном риске сторонней клавиатуры. |
| SEC-KEY-06 | Замена/удаление — явные действия. При замене корректно обработать сбой SecureStore: не сообщать об успешной замене до записи. При удалении ошибка хранилища показывается явно. |
| SEC-KEY-07 | Исключить SecureStore из Android cloud backup и переноса устройства; проверить правила в release-сборке. После переустановки/восстановления ключ вводится заново. |
| SEC-KEY-08 | Если SecureStore недоступен или запись/чтение невозможны, остановить подключение; никакого fallback в незашифрованный файл. |
| SEC-KEY-09 | Удаление локального ключа не отзывает его у OpenRouter. Показать инструкцию: при подозрении на утечку немедленно отозвать ключ в аккаунте провайдера, проверить расходы и создать отдельный новый ключ. |

Биометрическое подтверждение каждого запроса не включено в исходный объём. Это возможное усиление после оценки удобства; не считать его реализованной защитой MVP.

## 3. Сеть

- SEC-NET-01: только HTTPS, системная проверка сертификата/имени хоста; cleartext запрещён в release. Не отключать TLS-проверку для отладки.
- SEC-NET-02: фиксированный origin `https://openrouter.ai`; allowlist API-путей. Клиентский ввод не меняет base URL, заголовки авторизации или адрес по инструкции ИИ.
- SEC-NET-03: ключ передаётся только в `Authorization: Bearer …`, не URL/query, тексте промпта, имени файла, метаданных карточки или параметрах внешней ссылки.
- SEC-NET-04: не следовать редиректам API с ключом на другой origin; не выполнять запросы по URL из ответов модели. Поведение транспорта проверить на целевой Android-сборке.
- SEC-NET-05: разрешённые model IDs берутся из внутреннего ограниченного каталога, не из произвольного поля пользователя. Каталог из сети может уточнить доступность, но не расширить allowlist.
- SEC-NET-06: не выполнять tool calls, JS, HTML или команды модели. Ответ — данные, отображаемые нативным текстом. Ссылки не открываются автоматически.
- SEC-NET-07: сертификатное pinning не требуется для первого MVP; стандартная TLS-проверка обязательна. Pinning не защищает ключ от инструментирования на скомпрометированном телефоне.

## 4. Логи, сборка и Git

- SEC-LOG-01: запрещено логировать ключ, Authorization, тела запросов/ответов, аудио, тексты и состояние поля ввода. Ошибки провайдера нормализуются, сырые диагностические ответы в UI не выводятся.
- SEC-LOG-02: допустимы локальные диагностические код ошибки, тип операции, модель, длительность, HTTP-статус; без ключа и содержимого. Внешние crash-reporting/аналитика не включаются автоматически.
- SEC-LOG-03: release без debug-экранов, сетевых инспекторов и подробного console-вывода; logcat проверяется на тестовом ключе.
- SEC-GIT-01: в Git только приложение, не секреты, память агента, пользовательские запросы или служебные заметки. `.env*` с реальными значениями, key/signing-файлы, dumps и логи исключены. Исключения `.env.example` — только с пустыми/заведомо фиктивными значениями.
- SEC-GIT-02: `.gitignore` не удаляет уже закоммиченный секрет. При обнаружении — отозвать ключ, проверить историю и артефакты сборки; очистку истории согласовать отдельно.
- SEC-BUILD-01: CI/OTA/подпись сборки не получают пользовательские OpenRouter-ключи. Существующий серверный ключ прототипа в мобильный продукт не переносится.
- SEC-BUILD-02: секреты подписи/публикации защищаются отдельно от OpenRouter; права минимальны. Обновления и пакеты зависимостей фиксируются lockfile; лицензии проверяются.

## 5. Приватность и устройство

- SEC-DATA-01: SQLite и аудио в приватной sandbox приложения. Не хранить чувствительные материалы в общедоступной папке по умолчанию; без разрешения на широкий доступ к накопителю.
- SEC-DATA-02: для MVP предлагается отключить автоматические cloud backup/transfer всех учебных данных; предупредить о потере при удалении приложения. Это не означает шифрование SQLite приложением.
- SEC-DATA-03: ключ хранится отдельно. Для учебных данных baseline — sandbox и защита Android разблокировкой/шифрованием устройства. SQLCipher не требуется автоматически; риск доступа на разблокированном/скомпрометированном телефоне раскрыть.
- SEC-DATA-04: микрофон запрашивать непосредственно перед записью, только foreground. Не запрашивать контакты, геолокацию, весь накопитель или доступ к телефону для функций MVP.
- SEC-DATA-05: на экране ввода ключа запретить скриншоты/запись экрана штатным Android-механизмом; убрать чувствительный снимок из recent apps при фоне. Проверить TalkBack и ограничения системной защиты. Не обещать защиту от внешней камеры.
- SEC-DATA-06: перед первым запросом получить подтверждение передачи данных OpenRouter и конечному провайдеру модели. Отправлять только необходимое: аудио для А, источник для Б, Б для перевода, короткий контекст для слова.
- SEC-DATA-07: не отправлять весь словарь, журнал, идентификаторы телефона и другие записи для одной операции. Модельные настройки и инструкции передаются только в требуемом объёме.
- SEC-DATA-08: локальное удаление не гарантирует удаления у внешних провайдеров. Перед публичным выпуском актуализировать политику приватности, условия OpenRouter/исполнителей и декларации магазина по фактическим потокам.
- SEC-DATA-09: ZDR или «не использовать для обучения» не обещать без подтверждения endpoint/настроек аккаунта; это может ограничить доступные модели.
- SEC-DATA-10: временные файлы убирать после ошибки/отмены и при следующем запуске; удалять только принадлежащие приложению файлы. Не повреждать готовые записи.
- SEC-DATA-11: резет настроек не является очисткой: по D-10 сохраняет ключ, материалы, словарь и прогресс. Общую команду удаления всех данных не включать в MVP. Исключение без подтверждения — только немедленное удаление свежего аудио без связанных артефактов по AUD-08.
- SEC-DATA-12: не добавлять app lock, регистрационные формы, OIDC/OAuth, Replit Auth или собственные JWT в MVP. Пользователь использует блокировку телефона/средства защиты приложений ОС, если они доступны на его устройстве.
- SEC-DATA-13: `https://t.me/ivTelegram` открывается только по явному нажатию контакта разработчика. Это не API-endpoint: никогда не прикладывать к ссылке ключ, материал, словарь, промпт или диагностику.

## 6. Защита расходов и устойчивость

- SEC-COST-01: все обращения используют пользовательский ключ; нет общего скрытого ключа или fallback на средства владельца.
- SEC-COST-02: А и Б — отдельные явные действия; Перевод автоматически следует за успешной Б. Общую платность описать один раз при подключении/передаче данных и в настройках; не требовать предупреждения об оплате перед повтором А или каждой операцией. Нет автоповторов при таймауте/402/429 или бесконечного повторения при ошибке структуры ответа.
- SEC-COST-03: лимиты длины/аудио/токенов, одна активная цепочка, защита повторного нажатия. Клиентские лимиты ограничивают случайные расходы, но не обеспечивают жёсткий бюджет.
- SEC-COST-04: рекомендовать отдельный ключ с ограничением средств в аккаунте OpenRouter. Удаление/отмена на клиенте может не остановить уже начатое списание.
- SEC-COST-05: новый ключ не считается действующим только из-за подходящего формата; проверять доступ разрешённым endpoint без платной генерации, если он доступен. Не выводить в UI сырые сведения ответа с секретами.
- SEC-VALID-01: валидировать поля и размеры до отправки и ответа до сохранения; ошибку не заменять пустым «успешным» результатом. Текст/инструкция не могут менять транспорт или исполнять инструменты.
- SEC-VALID-02: редактируемые промпты могут изменить качество результата, но не могут читать SecureStore, менять адрес запроса или получать ключ в своём контексте. Ключ не включать ни в один промпт; настройку без подтверждённой поддержки не выдавать за применённую.

## 7. SEC-TEST — обязательная проверка до выпуска

| Проверка | Критерий |
|---|---|
| APK/AAB, bundle, assets, OTA | Нет реальных ключей; нет общего ключа прототипа. |
| SQLite, AsyncStorage, обычные файлы, cache | Тестовый пользовательский ключ нигде не хранится открыто. |
| logcat, консоль, сообщения ошибок | Нет ключа/Authorization, аудио и приватных текстов. |
| Сохранение/замена/удаление/ошибка SecureStore | Нет открытого fallback, ложного успеха или восстановления удалённого ключа поздним ответом. |
| Android backup/restore и device transfer | Ключ не переносится; правила учебных данных соответствуют D-05. |
| Экран ключа, recent apps, буфер обмена | Сохранённый ключ не раскрывается и не копируется; запрет скриншота работает в release. |
| TLS и редирект на контролируемый другой origin | Сертификатные ошибки отклоняются; Authorization не уходит на другой origin. |
| Поддельный model ID, URL, слишком длинный текст | Отказ до запроса; никакой произвольной маршрутизации/обрезки. |
| Инструкция в А/Б/ответе модели | Не меняет endpoint, не получает ключ, не запускает инструменты/внешние ссылки. |
| Двойное нажатие, таймаут, cancel, 402/429 | Нет автоматических повторных платных запросов и скрытой подмены модели. |
| Резет настроек | Defaults и промпты восстановлены, ключ/материалы/словарь/прогресс сохранены; нет скрытой очистки БД. |
| Доступ в приложение | Нет собственной регистрации, входа, скрытого аккаунта или общего серверного ключа. |
| Контакт разработчика | Открывается только по нажатию, без ключа/учебных данных в URL. |

Для проверки использовать отдельный ограниченный тестовый ключ, не публиковать его в отчётах. Документ задаёт требования; сам по себе он не является отчётом о прошедшем аудите.
